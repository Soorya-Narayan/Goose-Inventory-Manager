What is CIP Dashboard?
Background context and problem statement

Clean-In-Place (CIP) — The Industrial Context

Clean-In-Place (CIP) is an automated method of cleaning the interior surfaces of pipes, vessels, process equipment, and fittings without disassembling the system. It is a critical process in food & beverage manufacturing, pharmaceutical production, dairy processing, and chemical industries.

A typical CIP cycle involves multiple sequential cleaning steps — Pre-rinse with water, Caustic wash (hot NaOH solution), Intermediate rinse, Acid wash (HNO3 solution), and Final rinse. Each step requires precise control of temperature, flow rate, chemical concentration, pressure, and timing. Even small deviations can lead to contamination, quality failures, or regulatory non-compliance.

The Problem with Traditional Systems

Conventional SCADA (Supervisory Control and Data Acquisition) and HMI (Human-Machine Interface) systems display raw sensor readings but offer no intelligence. Operators can only see what is happening right now — not what is about to go wrong. Equipment failures, sensor drift, and process deviations are discovered only after they occur, causing costly downtime and compliance failures.

Our Solution — CIP Dashboard

CIP Dashboard is a next-generation, enterprise-grade web application built by Goose Digital that transforms industrial CIP operations. It connects directly to existing PLCs (Programmable Logic Controllers) through standard industrial protocols, visualizes all data in a beautiful modern interface, and uses Artificial Intelligence to predict failures before they happen.

In Simple Words

Think of CIP Dashboard as a "smart brain" that watches your entire cleaning process 24/7, tells you exactly what is happening right now, warns you before anything goes wrong, and learns from historical patterns to keep improving. All of this runs in your web browser — no special software needed.

System Architecture
Complete data flow from PLC to browser dashboard

How Data Flows — The Complete Pipeline

The system is organized in four distinct layers. Data flows from physical field devices all the way to the operator's browser in under 3 seconds.

FIELD [PLC S7-1200/S7-1500] + [Sensors: Temp, Flow, pH, Conductivity, Pressure] │ │ ← OPC UA / MQTT / IIH Essentials Protocol → │ EDGE [IIH Essentials] ──────────── [InfluxDB Time-Series Database] │ │ ← REST API calls over Docker internal network → │ APP [Flask REST API] + [ML Microservice — 7 AI Models] │ │ ← Nginx Reverse Proxy (HTTPS) → │ UI [React 18 Dashboard] ← Runs in any web browser, tablet, or phone

Layer 1: Field Level — PLC & Sensors

PLC (Programmable Logic Controller) is the brain of the physical factory system. We use Siemens S7-1200 and S7-1500 series PLCs. These controllers read data from physical instruments attached to the CIP equipment:

  • Temperature Sensors — Measure supply and return temperatures (°C). Critical for cleaning effectiveness.
  • Flow Sensors — Measure liquid flow rate (L/hr). Ensures proper turbulence for cleaning.
  • Conductivity Sensors — Measure the concentration of cleaning chemicals (mS/m). Indicates chemical strength.
  • pH Sensors — Measure acidity/alkalinity. Verifies correct chemical type and concentration.
  • Pressure Sensors — Monitor system pressure. Detects blockages or pump issues.
What is a PLC Tag?

A "tag" is a named variable in a PLC that holds a sensor value. For example, PHE01.Temp_Supply is a tag holding the supply temperature reading. Our system reads 1000+ such tags from the PLC in real-time.

Layer 2: Edge Level — IIH Essentials & InfluxDB

IIH Essentials (Industrial Information Hub) is a Siemens software running on Siemens Industrial Edge hardware. It acts as a bridge between the PLC and the rest of the software system. It uses OPC UA (OPC Unified Architecture) — the international standard protocol for industrial data exchange — to read PLC tags at high frequency and store them in a time-series database.

InfluxDB is a purpose-built time-series database. Unlike regular databases, it is optimized for storing millions of timestamped sensor readings with sub-millisecond precision. All historical process data is stored here, enabling both real-time visualization and historical analysis.

Layer 3: Application Level — Flask API & ML Service

Flask (Python) is the REST API server that connects the database to the frontend. It handles all data requests, user authentication, alarm management, and report generation. It runs using Gunicorn — a production-grade Python web server.

The ML Microservice is a separate Flask application (port 5002) that hosts all 7 AI/ML models. It runs independently and is called by the main API every 3 seconds to get fresh predictions for each AI diagnostic module.

Layer 4: UI Level — React Dashboard

React 18 (a JavaScript library by Meta) builds the browser-based user interface. It creates a dynamic, responsive, and interactive dashboard that updates automatically as new data arrives. Nginx serves the React app as a reverse proxy, providing HTTPS security and load balancing.

All four layers are bundled into Docker containers and coordinated using Docker Compose — making the entire system portable and easy to deploy on any compatible hardware.

Dashboard Modules
Every feature explained in plain language

Module 1: Live KPI Monitoring

What it does

Large, at-a-glance cards display the five most critical process parameters — refreshed automatically every 3 seconds. Each card shows current value, unit, trend direction (up/down/stable), and color-coded status (green = normal, amber = warning, red = critical).

Temperature (°C)
Shows supply and return temperatures of the cleaning solution. Must be within setpoint range for effective cleaning. Too low = insufficient cleaning; too high = equipment damage risk.
Flow Rate (L/hr)
Volume of liquid passing through per hour. Sufficient flow creates turbulence needed to physically clean pipe surfaces. Drops in flow may indicate blockages or pump failures.
Conductivity (mS/m)
Electrical conductivity measures the ionic content of the solution, which directly relates to chemical concentration. Used to detect phase transitions (water → chemical → rinse).
Pressure & pH
Pressure shows system health and detects blockages. pH (acidity) confirms the correct chemical type is present and at the right concentration for the cleaning step.

Module 2: CIP Cycle Tracking

A visual progress timeline shows exactly which step of the CIP cycle is currently running — Pre-rinse, Caustic wash, Intermediate rinse, Acid wash, or Final rinse. Each step has defined duration, temperature, and flow targets. The system instantly alerts operators when any parameter deviates from the expected profile.

Module 3: Trend Charts & Monitoring

Interactive time-series charts display historical parameter values. Operators can switch between Live Mode (last 30 minutes of data) and Historical Mode (any date range). Multiple parameters can be overlaid on the same chart for correlation analysis. All data can be exported to CSV for use in Excel or compliance software.

Module 4: Alarm Management

The alarm system uses a three-priority model:

  • Critical (Red) — Immediate action required. Process is at risk. Example: temperature 10°C below setpoint.
  • Warning (Amber) — Attention needed soon. Example: conductivity trending downward.
  • Info (Blue) — Informational. Example: new CIP cycle started.

Each alarm must be acknowledged by an operator (with their user ID and timestamp recorded). This creates a complete audit trail for regulatory compliance.

Module 5: Performance Analytics

Aggregated metrics for management reporting:

  • OEE (Overall Equipment Efficiency) — Combined measure of equipment availability, performance, and quality. Target: 85%+.
  • Average Cycle Time — How long each CIP cycle takes. Shorter cycles = higher throughput.
  • Water & Energy Cost — Actual utility consumption translated into cost (₹). Configurable rates per litre/kWh.
  • Usage Breakdown — Doughnut chart showing % cost split between water (45%), chemicals (35%), and energy (20%).

Module 6: Reports & Compliance

The Reports module generates cycle-specific PDF reports containing all parameter histories, alarm events, and operator actions. Data is logged in compliance with FDA 21 CFR Part 11 — the US regulatory standard for electronic records in pharmaceutical manufacturing. Role-based access controls (Admin / Operator / QA Supervisor) ensure data integrity.

GOOSE AI Diagnostics Engine
The key differentiator — 7 ML models explained
★ Why AI Diagnostics is Our Biggest Differentiator

No conventional SCADA or HMI system offers embedded, real-time machine learning diagnostics. CIP Dashboard's AI engine runs 7 specialized models simultaneously on live PLC telemetry, providing capabilities that simply do not exist in any off-the-shelf industrial monitoring product. This alone justifies the platform from a maintenance cost perspective.

The Model — Random Forest Classifier

All predictive models use the Random Forest algorithm — an ensemble learning method that combines hundreds of individual decision trees to make robust, accurate predictions. The model is trained on historical CIP data collected from real production runs (full-day CSV datasets exported from PLC/IIH).

Key statistics: 99.96% accuracy, 11 input feature vectors, 3-second inference interval.

The 11 input features used by GOOSE-ALPHA (primary failure prediction model):

  • supply_temp — Supply temperature (°C)
  • return_temp — Return temperature (°C)
  • flow — Flow rate (L/hr)
  • conductivity — Conductivity (mS/m)
  • remaining_time — Seconds remaining in current step
  • step_status — Current CIP step (encoded as integer)
  • recipe — Which CIP recipe is running
  • valve_status — Valve open/close state
  • pump — Pump running status
  • hour — Hour of day (time-based pattern)
  • day_of_week — Day of week (usage pattern)

Deployment Options
How and where CIP Dashboard can be installed
  1. Siemens Industrial Edge (Primary — On-Premise)
    The preferred deployment. CIP Dashboard is packaged as an Industrial Edge App (.tar file). It runs directly on Siemens Industrial Edge hardware co-located with the factory equipment, reading PLC data through IIH Essentials. No cloud connection required. Maximum data security and minimum latency.
  2. Docker Compose — Any Linux Server
    For facilities with existing server infrastructure. Deploy on any Ubuntu/Debian server using a single docker compose up command. Connect via OPC UA to PLCs over the factory network. Suitable for on-premise servers without Siemens Edge hardware.
  3. Cloud Deployment (Azure / AWS)
    For multi-site deployments or organizations with cloud infrastructure. CIP data is securely transmitted from edge devices to cloud containers. Enables centralized monitoring of multiple factories from a single interface. Requires secure VPN connectivity to factory networks.
Docker Compose Architecture

The system runs 3 Docker containers: cip-backend (Flask API on port 5001), cip-ml-api (ML service on port 5002), and cip-frontend (React app served by Nginx on port 5000). They communicate over a private Docker bridge network called cip-network. An external InfluxDB instance is connected for time-series storage.
